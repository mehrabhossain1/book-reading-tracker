# Book Tracker — Version 1 Plan

**Goal (v1):** Track how far I've read in *several books at once*, so I can put a book down,
come back weeks later, and immediately know the exact page to resume from.

**Constraint:** Build it as a single-user tool today, but on foundations that become a
multi-user SaaS without a rewrite.

**Non-goal (v1):** Fancy/animated UI, social features, book discovery APIs, mobile app.

---

## 1. The core problem, stated precisely

Parallel reading breaks the normal "one bookmark" model. What I actually need per book:

| Question | v1 answer |
|---|---|
| Which books am I *actively* reading right now? | `status = 'reading'` list, sorted by last activity |
| What page am I on in each? | `book.current_page` |
| What page do I start from next? | `current_page + 1` — pre-filled in the log form |
| How far through am I? | `current_page / total_pages` |
| Did I actually read this week? | append-only `reading_session` log |
| Which book have I neglected? | `last_read_at` staleness on the library list |

Everything in v1 exists to answer those six questions in under two taps.

## 2. Stack decision (researched 2026-08)

| Layer | Choice | Version | Why |
|---|---|---|---|
| Framework | **Next.js (App Router)** | 16.3.x | RSC + Server Actions; the ecosystem default |
| Runtime | React | 19.2.x | Ships with Next 16 |
| Language | TypeScript `strict` | 5.x | Non-negotiable for a SaaS trajectory |
| Auth | **Better Auth** | 1.7.x | See note below |
| DB | **PostgreSQL** | — | URL supplied by me (Neon/Supabase/local) |
| ORM | **Drizzle ORM** + drizzle-kit | 0.45 / 0.31 | Edge-safe, tiny, SQL-level control, no query-engine binary |
| Styling | **Tailwind CSS v4** | 4.3.x | Zero-config CSS-first, RSC-safe |
| Components | **shadcn/ui** | latest | Code we own, not a versioned dependency |
| Validation | **Zod** | 4.x | One schema shared by client form + server action |
| Forms | react-hook-form + `@hookform/resolvers` | latest | Standard pairing with Zod |
| Env safety | `@t3-oss/env-nextjs` | latest | Fails the build on a missing/invalid env var |
| Tests | Vitest (unit) | latest | Progress math is the part worth unit-testing |

### Why Better Auth over NextAuth / Clerk

- **NextAuth (Auth.js)** entered maintenance mode in early 2026 — security patches only.
  Starting a new project on it is starting on a dead end.
- **Clerk** is the fastest path to a login box, but it's per-MAU pricing and my users live
  in *their* database, not mine. For a product I intend to scale, that's a permanent tax
  and a permanent data-ownership problem.
- **Better Auth** keeps users in my own Postgres, is TypeScript-native, and ships
  email/password, OAuth, magic links, 2FA and **organizations/teams** as first-party
  plugins. The organization plugin is exactly the seam v2 needs for multi-tenancy —
  I get it by flipping a flag, not by migrating auth providers.

**v1 auth surface:** email + password, with Google OAuth wired but optional (only enabled
if I supply the client credentials). Sessions are DB-backed with HTTP-only cookies.

### Next.js 16 specifics to respect

- `middleware.ts` is now **`proxy.ts`** — route protection goes there.
- The proxy does an *optimistic* cookie check only. **Every server action and every
  data query re-validates the session server-side.** The proxy is UX, not security.

## 3. Data model

### 3.1 Auth tables (generated by Better Auth CLI)
`user`, `session`, `account`, `verification` — untouched by hand.

### 3.2 Domain tables

```
book
  id            uuid pk
  user_id       text  fk -> user.id  on delete cascade      [indexed]
  title         text  not null
  author        text
  total_pages   integer not null check (> 0)
  cover_url     text
  status        enum('reading','paused','finished','want_to_read','abandoned')
                default 'reading'                            [indexed w/ user_id]
  current_page  integer not null default 0  check (>= 0)
  started_at    timestamptz
  finished_at   timestamptz
  last_read_at  timestamptz                                  [sort key]
  created_at    timestamptz not null default now()
  updated_at    timestamptz not null default now()

reading_session            -- append-only log, never updated in place
  id            uuid pk
  book_id       uuid fk -> book.id on delete cascade         [indexed]
  user_id       text fk -> user.id on delete cascade
  start_page    integer not null      -- inclusive
  end_page      integer not null      -- inclusive, >= start_page
  pages_read    integer not null      -- end_page - start_page + 1, stored
  note          text
  read_at       timestamptz not null default now()
  created_at    timestamptz not null default now()
```

**Design notes**

- `book.current_page` is **denormalized on purpose**. The library screen must render
  without aggregating a log table per row. The append-only `reading_session` is the audit
  trail; the two are written together **inside one transaction**, never separately.
- `pages_read` is stored, not computed at read time, so weekly/streak stats are a plain
  `SUM` over an indexed range.
- **Every domain row carries `user_id`** from day one — even though there's one user
  today. Every query filters on it. This is the single decision that makes the SaaS
  migration a schema addition instead of a rewrite.
- Logging progress **backwards** (re-reading, or correcting a typo) is allowed: the
  session is recorded, but `current_page` only moves forward to `max(current, end_page)`.
  Correcting a mistake is an explicit "edit" path, not a silent overwrite.

### 3.3 Deliberately deferred to v2
Shelves/tags, notes & highlights, reading goals, editions/ISBN lookup, audiobook +
percentage-based tracking, organizations/sharing, Stripe billing.

## 4. Screens & UX — grounded in Mobbin references

Design language: quiet, dense, text-first. Type and spacing do the work; no animation.

### 4.1 `/library` — the home screen *(primary reference: [Blinkist "My History"](https://mobbin.com/screens/66341d2e-aa6d-47c4-a5e8-cc3e2d3a564b))*

The Blinkist pattern is almost exactly this product: a segmented **In progress / Finished**
control over a vertical list, each row carrying cover, title, author, a thin progress bar,
and a "N left" affordance — plus a persistent **Continue reading** bar pinned at the bottom.

- Segmented control: `Reading` · `Paused` · `Finished`
- Row = cover thumbnail · title · author · progress bar · `p. 142 of 380 · 238 left`
- Row overflow menu (`…`, as in Blinkist): Edit, Pause, Mark finished, Delete
- Rows sorted by `last_read_at desc` — the neglected book sinks, visibly
- Sticky bottom bar: **Continue reading — <most recent book>** → opens the log dialog
- Empty state: single centered "Add your first book" CTA
- Compact row density borrowed from
  [Speechify's library](https://mobbin.com/screens/7684e3d6-1176-40ec-84f4-de89417dd7ec) and
  [Matter's queue](https://mobbin.com/screens/f6a923a9-d1de-4b38-93b9-f2b7b797c288) (web
  sidebar + flat list — the desktop shell for this app)

### 4.2 Log progress dialog — *the* interaction *(references: [Fable](https://mobbin.com/screens/052c1378-69dd-4674-be8c-e02a46463b0a), [Goodreads "Updating progress"](https://mobbin.com/flows/e544028f-48f3-4b92-ad4b-bb162e33e364))*

Fable's card is the model: a `Progress` row with two page inputs, a unit selector, a
`Mark as finished` checkbox, and one dark full-width **Update** button. Goodreads' sheet
confirms the copy pattern — *"I'm on page ___"* with a Page # / Percent toggle.

Ours, opened from any row:

```
  Atomic Habits
  ┌─────────────────────────────────────────┐
  │  From page  [ 143 ]   to page  [ ___ ]  │   ← "from" pre-filled = current_page + 1
  │             ▸ resuming where you left off│
  │  Note (optional)  [_____________________]│
  │  ☐ I finished this book                  │
  │            [      Update      ]           │
  └─────────────────────────────────────────┘
```

- The pre-filled *from* page **is the feature** — it's the whole reason this app exists.
- `to page` is the only required input. One field, one tap, done.
- Checking "I finished" sets `end_page = total_pages`, `status = 'finished'`, `finished_at = now()`.
- On submit the dialog closes, a toast confirms the new page, and the action's
  `revalidatePath` + `router.refresh()` repaint the list. (Considered `useOptimistic`
  and dropped it: the list is server-rendered, and threading optimistic state through
  the RSC boundary buys milliseconds at the cost of a second source of truth.)

### 4.3 `/books/[bookId]` — detail *(reference: [Goodreads activity timeline](https://mobbin.com/screens/be982c85-4740-4850-93a8-5f219bdf3147))*

Cover + metadata header · large progress bar with `37% · page 142 of 380` · **Update your
progress** button · a reverse-chronological session timeline (`+18 pages · pages 125–142 ·
3 days ago · "great chapter on habit stacking"`) · edit / status actions.

### 4.4 `/books/new` — add a book
Title (required) · Author · Total pages (required) · Cover URL (optional) · Start now?
Manual entry only in v1; ISBN/Open Library lookup is a v2 slot-in behind the same form.

### 4.5 `/stats` — deliberately small
Pages this week · current streak · books finished this year · a 7-day bar. The
[Goodreads Reading Challenge](https://mobbin.com/screens/981252f7-d124-45df-af48-dd7ad1b86f1e)
and [Literal goal](https://mobbin.com/screens/0276019a-e4ea-45ac-8ab9-2f19712bfacb) screens
are the v2 target; v1 ships four numbers.

### 4.6 `/sign-in`, `/sign-up` *(references: [Flodesk](https://mobbin.com/screens/d606b5eb-929c-41f0-a1c7-67fb25ef5417), [ElevenLabs](https://mobbin.com/screens/454f212d-aaac-4307-b45e-df8ca4eb6248))*

Centered column on plain ground, wordmark, `Welcome back`, OAuth button first, `or`
divider, email + password, one dark full-width submit, footer link to the opposite route.
Inline field errors from the shared Zod schema. No split-screen hero, no illustration.

### 4.7 App shell
Desktop: narrow left sidebar (Library · Stats · Settings) + max-width content column —
the Matter layout. Mobile: bottom tab bar. Dark mode from day one via Tailwind v4 tokens.

## 5. Architecture & code patterns

```
src/
  app/
    (auth)/sign-in/page.tsx
    (auth)/sign-up/page.tsx
    (app)/layout.tsx                  ← requireUser() guard + shell
    (app)/library/page.tsx
    (app)/books/new/page.tsx
    (app)/books/[bookId]/page.tsx
    (app)/stats/page.tsx
    (app)/settings/page.tsx
    api/auth/[...all]/route.ts        ← toNextJsHandler(auth)
    layout.tsx  ·  page.tsx  ·  globals.css
  proxy.ts                            ← Next 16 route protection (optimistic)
  db/
    index.ts                          ← pooled client, dev-safe singleton
    schema/{auth,books,index}.ts
  modules/
    books/{schema,queries,actions}.ts · components/
    progress/{schema,queries,actions}.ts · components/
    stats/queries.ts
  components/ui/                      ← shadcn primitives
  components/                         ← shared app components
  lib/{auth,auth-client,require-user,safe-action,utils,env}.ts
drizzle/                              ← generated SQL migrations (committed)
```

**Rules the code follows**

1. **Feature modules, not layer folders.** `modules/books/*` holds its schema, queries,
   actions and components together. New SaaS features arrive as new folders.
2. **Reads = RSC + `queries.ts`.** Server Components call typed query functions directly.
   No client-side fetching, no API layer, no TanStack Query in v1 — there is nothing for
   it to do that RSC doesn't already do better here.
3. **Writes = Server Actions**, each wrapped by a `authedAction` helper that (a) resolves
   the session server-side, (b) parses input with the Zod schema, (c) injects `userId`,
   (d) returns a typed `{ ok } | { error }`. Actions never trust a client-supplied `userId`.
4. **Ownership check on every row.** Every query and mutation is scoped
   `where(and(eq(book.userId, userId), eq(book.id, id)))` — never by `id` alone.
5. **One Zod schema per operation**, imported by both the RHF form and the action.
6. **Transactional writes.** Logging progress inserts the session *and* updates the book
   in a single `db.transaction`.
7. **Pure domain logic is pure.** `progressPercent`, `pagesRemaining`, `nextStartPage`,
   `streakFrom(sessions)` live in plain functions and are unit-tested with Vitest.
8. **`revalidatePath`** in every action, plus `router.refresh()` on the client, so a
   mutation repaints from the server rather than from a guessed local copy.
9. **Env vars validated at build time** — a missing `DATABASE_URL` fails the build, not
   the first request.

**Environment**
```
DATABASE_URL=            # you'll provide
BETTER_AUTH_SECRET=      # openssl rand -base64 32
BETTER_AUTH_URL=http://localhost:3000
GOOGLE_CLIENT_ID=        # optional
GOOGLE_CLIENT_SECRET=    # optional
```

## 7. Deliberate seams for the SaaS version

None of these are built in v1 — each is a place where v1 *doesn't* block v2.

- **`user_id` on every row + every query scoped to it** → the multi-tenant boundary
  already exists and is already enforced.
- **Better Auth organization plugin** → teams/shared shelves become `organization_id`
  alongside `user_id`, no auth migration.
- **Append-only `reading_session`** → future analytics, streaks, year-in-review and
  goal tracking are queries over data v1 is already collecting. Nothing to backfill.
- **Feature-module folders** → billing, imports, public profiles arrive as siblings.
- **Server Actions behind a typed `authedAction`** → adding rate limiting, plan-tier
  gating or audit logging is one edit to the wrapper, not N edits to N actions.
- **Manual book entry behind a form component** → an ISBN/Open Library lookup drops into
  the same form and the same action.
- **Own the users in own Postgres** → no per-MAU pricing wall, no migration when it grows.

## 9. Verified vs. not

**Verified:** typecheck, lint, production build, 22 unit tests over the progress and
streak math, and the generated migration SQL (all CHECK constraints and indexes
present in `drizzle/0000_skinny_maximus.sql`).

**Not yet verified — needs the database:** applying the migration, sign-up/sign-in
against real tables, and the log-progress transaction end to end.

**One thing worth recording:** `@better-auth/cli` still publishes 1.4.x while the
library is on 1.7.x, and its generated schema omits `account.issuer`, which 1.7
marks required. Checked against `getAuthTables()` from `@better-auth/core@1.7.1`
and added by hand; sign-up would have failed at runtime otherwise. Anyone
regenerating that file has to re-add it.
